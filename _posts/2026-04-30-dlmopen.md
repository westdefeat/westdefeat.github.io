# 从 dlopen 到 dlmopen：在一个进程里装下两套同名动态库

这事起因很朴素：有两套动态库，ABI 看起来一样，导出的函数名也一样，但实现不是一个版本。
如果只用 `dlopen`，到底能不能在同一个进程里同时调用它们？

答案是：普通 `dlopen` 很难优雅解决，`dlmopen` 可以。

## 先说熟悉的 dlopen

`dlopen` 是运行时加载动态库最常见的入口。程序启动时不直接链接某个 `.so`，
而是在需要的时候手动加载，再用 `dlsym` 拿函数地址。

大概长这样：

```cpp
void* handle = dlopen("./libplugin.so", RTLD_NOW);
auto run = reinterpret_cast<void (*)()>(dlsym(handle, "run"));
run();
dlclose(handle);
```

它很适合插件系统、可选依赖、按需加载这类场景。问题是，它仍然活在默认的动态链接命名空间里。
同一个进程里已经加载过的库、全局符号、依赖解析顺序，都会影响后面加载的库。

当两份库都叫 `libfoo.so`，里面都导出 `foo_init`，但行为不同，事情就开始变得微妙了。

## 动态链接器在背后做了什么

Linux 下的 ELF 动态链接不是简单地“按路径打开一个文件”。动态链接器会维护已加载对象、
解析依赖、绑定符号，并按一定规则查找 `.so`。

一次典型加载大概会经历几步：

1. 找到目标 `.so` 文件。
2. 读取 ELF 里的 `DT_NEEDED`，继续加载它依赖的库。
3. 把这些库放进当前进程的动态链接对象列表里，也就是 link map。
4. 做重定位，把还没确定地址的函数、全局变量绑定到某个具体定义上。

常见影响因素有几个：

- `LD_LIBRARY_PATH`：给动态链接器额外的搜索目录，常用于调试或临时切换依赖。
- `RPATH` / `RUNPATH`：写进 ELF 里的运行时搜索路径，CMake 里的 `BUILD_RPATH` 就会影响它。
- `LD_PRELOAD`：在程序启动时提前塞入一个库，常用于 hook、替换 malloc、压测或排查问题。
- `RTLD_GLOBAL` / `RTLD_LOCAL`：控制库里的符号是否放进全局可见范围。

这些机制都很有用，但它们本质上还是围绕同一个默认命名空间打转。
你可以影响“先找谁”“从哪里找”“谁覆盖谁”，却很难说：

> 这一套依赖树用 A 版本，另一套依赖树用 B 版本，彼此不要串。

这就是 `dlmopen` 要解决的痛点。

## dlmopen 多出来的东西：namespace

`dlmopen` 是 glibc 的 GNU 扩展，不是 POSIX 标准接口。它和 `dlopen` 最大的区别是：
加载库时可以指定 link-map namespace。

普通 `dlopen` 可以粗略理解为：

```text
base namespace
  main
  libc.so
  libfoo.so
  libbar.so
```

所有东西都在这个默认 namespace 里。后加载的库在解析符号时，会看到这里已有的一部分对象。
如果 `libfoo.so` 已经出现过，后面再来一个名字、SONAME、符号都相同的库，就很容易被已有状态影响。

`dlmopen(LM_ID_NEWLM, ...)` 则是新开一个 link map：

```text
base namespace              namespace 1                namespace 2
  main                        libdemo_provider.so(v1)    libdemo_provider.so(v2)
  libc.so                     libdemo_app.so             libdemo_app.so
```

每个 namespace 都有自己的已加载对象列表。库的 `DT_NEEDED` 依赖、重定位和符号查找，
都会围绕它所在的 namespace 展开。这样，两份都叫 `libdemo_provider.so` 的库就不再需要在同一张符号表里抢位置。

```cpp
void* provider = dlmopen(LM_ID_NEWLM, "./v1/libdemo_provider.so", RTLD_NOW | RTLD_LOCAL);

Lmid_t namespace_id;
dlinfo(provider, RTLD_DI_LMID, &namespace_id);

void* app = dlmopen(namespace_id, "./libdemo_app.so", RTLD_NOW | RTLD_LOCAL);
```

这里有一个容易踩坑的点：`provider` 和 `app` 要在同一个 namespace 里。

`libdemo_app.so` 自己并不知道“我要用 v1 还是 v2”。它只知道自己需要一个
`libdemo_provider.so`，里面要有 `provider_compute` 这个符号。最终落到哪个实现，
取决于它被加载到哪个 namespace，以及那个 namespace 里已经有哪些对象。

所以流程是：

1. 用 `LM_ID_NEWLM` 加载 v1 的 provider，创建 namespace 1。
2. 通过 `dlinfo(..., RTLD_DI_LMID, ...)` 拿到 namespace 1 的 ID。
3. 再把 `libdemo_app.so` 加载进 namespace 1，让它解析到 v1。
4. 对 v2 重复同样的流程，得到 namespace 2。

换句话说，我们不是试图在一个房间里安排两个人都叫 `foo`，而是给他们分了两个房间。

这也解释了为什么单纯使用 `LD_LIBRARY_PATH` 或 `LD_PRELOAD` 不够。那些方法是在改变默认房间里的排队顺序；
`dlmopen` 是新开房间。

## 这个仓库做了一个最小实验

这里构造了三类东西：

- `src/provider.cpp`：底层动态库，导出 `provider_version`、`provider_compute` 等同名 C 符号。
- `build/v1/libdemo_provider.so`：版本 1，`provider_compute(x) = x + 100`。
- `build/v2/libdemo_provider.so`：版本 2，`provider_compute(x) = x + 200`。
- `src/app.cpp`：应用动态库，代码里直接调用 `libdemo_provider.so` 的符号。
- `src/dlmopen_experiment.cpp`：实验入口，同时创建两个 namespace，并交错调用两套库。

运行：

```bash
cmake -S . -B build
cmake --build build
cd build
./dlmopen_experiment
```

输出类似这样：

```text
v1 namespace=1
v2 namespace=2
v1 -> provider=provider-v1, compute(7)=107, counter=1, counter_addr=0x...
v2 -> provider=provider-v2, compute(7)=207, counter=1, counter_addr=0x...
v1 -> provider=provider-v1, compute(8)=108, counter=2, counter_addr=0x...
v2 -> provider=provider-v2, compute(8)=208, counter=2, counter_addr=0x...
```

这里有几个值得看的点：

- 两个 provider 文件都叫 `libdemo_provider.so`，SONAME 也一样。
- 两边导出的函数名一样，应用库 `libdemo_app.so` 的代码也一样。
- `v1` 一直调用到 `provider-v1`，`v2` 一直调用到 `provider-v2`。
- 两个 `counter` 各自从 1 开始，说明静态状态也没有混在一起。

## 用的时候要记住的边界

`dlmopen` 不是魔法隔离。两套库仍然在同一个进程地址空间里，崩溃、内存破坏、信号处理这些问题不会因为 namespace 消失。

另外，关键点不是“只把底层库用 `dlmopen` 加进去”，而是“把使用这些符号的应用库也加载到同一个 namespace 中”。
如果应用库已经在默认 namespace 里解析完符号，再加载另一套 provider 就晚了。

还有几个工程上要留意的地方：

- ABI 要真的兼容。函数名一样不代表参数、结构体布局、内存所有权约定也一样。
- 跨 namespace 传对象指针要克制。谁分配、谁释放，最好在同一套库边界内闭环。
- 不要指望它解决所有全局状态问题。文件描述符、环境变量、信号、线程这些仍然是进程级资源。
- 这是 glibc 扩展，迁移到其他 libc 或平台之前要重新评估。

所以这类方案比较适合：

- 同进程内验证两套 ABI 兼容库的行为差异。
- 旧 SDK 和新 SDK 函数名冲突，但上层调用边界相对清楚。
- 插件依赖树需要隔离，且能接受 glibc 扩展带来的平台限制。

如果目标是强隔离，还是应该上进程边界。`dlmopen` 更像是一把窄刀：用对地方很好用，用错地方会割手。
